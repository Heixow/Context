# 项目分工：三线并行

> 项目：Agent Context Visualizer
> 原则：先冻结接口，再三条线并行；同一时刻只有一人写主干，合并权按里程碑轮换。

## 一、分工总览

```
                ┌──────────────────────────────────────┐
                │  共享契约（M0 冻结，三人共同评审）      │
                │  shared/types.ts + IPC 方法清单        │
                └──────────────┬───────────────────────┘
        ┌──────────────────────┼──────────────────────┐
        ▼                      ▼                      ▼
┌────────────────┐   ┌──────────────────┐   ┌──────────────────┐
│ A 可视化与交互  │   │ C 核心上下文引擎   │   │ B 采集与模型接入   │
│ React 渲染层    │   │ 纯函数 + 单测      │   │ Electron 主进程    │
│ 列表/时间线/卡片 │   │ 指纹/匹配/校验/导出 │   │ 对话管线/代理/存储  │
└───────┬────────┘   └────────┬─────────┘   └────────┬─────────┘
        │  window.api / IPC   │  被 A、B 共同引用    │  提供 IPC 数据
        └─────────────────────┴──────────────────────┘
```

## 二、三个分工

### A. 可视化与交互

| 项       | 内容                                                                                                                     |
| -------- | ------------------------------------------------------------------------------------------------------------------------ |
| 职责     | 捕获/会话列表、会话折叠与展开、消息时间线、system/tools 面板、keep/drop 消息卡、token 分布图、自动匹配建议高亮、导出入口 |
| 目录     | `src/components/**`、`src/App.tsx`、`src/styles.css`                                                                     |
| 依赖     | 只通过 `window.api`（IPC）取数，不直接读文件、不 import Electron                                                         |
| 并行方式 | 第一阶段用 mock fixtures 独立开发，B/C 完成后替换数据源                                                                  |
| 交付物   | 可交互的完整界面，覆盖空态、错误态、长列表                                                                               |

### B. 采集与模型接入

| 项       | 内容                                                                                                                                                                                                     |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 职责     | 对话请求管线（组装 → 匹配 → 校验 → 调用 API → 落盘）、BYO API 配置与流式响应、反向代理（透传 / SSE / fail-open）、帧与 sidecar 存储、sessions.json、IPC handlers、API Key 的 safeStorage、窗口与生命周期 |
| 目录     | `electron/**`（main / preload / services）                                                                                                                                                               |
| 依赖     | 调用 C 的纯函数，不写 UI                                                                                                                                                                                 |
| 关键约束 | 密钥零落盘；代理只绑 `127.0.0.1`；上游异常不得影响转发                                                                                                                                                   |
| 交付物   | 两条链路可跑通：应用内对话、外部客户端代理                                                                                                                                                               |

### C. 核心上下文引擎

| 项       | 内容                                                                                                                        |
| -------- | --------------------------------------------------------------------------------------------------------------------------- |
| 职责     | 领域模型、请求体/转录解析、token 估算、消息指纹、有效选择合并、自动匹配、配对校验、Markdown 与 seed.json 导出、会话归并逻辑 |
| 目录     | 建议 `shared/lib/**`（别名 `@shared`），纯 TS，无 Electron / React 依赖                                                     |
| 依赖     | 不依赖 A、B；被 A 用于展示、被 B 用于发送前处理                                                                             |
| 并行方式 | 每个模块配 Vitest 单测，先出函数签名与桩，A/B 即可开工                                                                      |
| 交付物   | 全部纯函数与测试；配对校验能给出精确定位                                                                                    |

> 技术注意：匹配与校验发生在主进程发送前，引擎不能只放 `src/lib`，建议独立为 `shared/lib`，否则主进程会反向依赖渲染层目录。

## 三、接口边界（并行的前提）

| 边界     | 契约内容                                                                                                     | 冻结时间 |
| -------- | ------------------------------------------------------------------------------------------------------------ | -------- |
| A ↔ B    | IPC 方法：帧列表/详情、会话增删改、选择读写、导出、对话发送与流式事件                                        | M0       |
| A/B ↔ C  | 函数签名：`fingerprint`、`mergeSelection`、`applyMatches`、`validatePairing`、`exportMarkdown`、`exportSeed` | M0       |
| 共享类型 | `CapturedFrame`、`Session`、`SelectionFile`、`MessageFingerprint`                                            | M0       |

## 四、里程碑与并行节奏

| 里程碑        | A 可视化             | B 接入                      | C 引擎              |
| ------------- | -------------------- | --------------------------- | ------------------- |
| M0 契约冻结   | 评审类型与 IPC 清单  | 评审类型与 IPC 清单         | 起草并定稿          |
| M1 可跑分离   | mock 界面            | 代理采集 + 存储             | 纯函数 + 单测       |
| M2 对话模式   | 接真实数据           | 对话管线 + 流式 + 密钥      | 匹配/校验接入主进程 |
| M3 精炼闭环   | keep/drop + 建议模式 | sidecar 读写 + 自动匹配调用 | 导出 + 校验定位     |
| M4 代理与交付 | 会话手动合并 UI      | 代理模式 + 打包             | 性能与边界用例      |

M0 约 1–2 天，M1 起三条线真正并行。

## 五、写入轮换规则

同一时刻只允许一人写主干（`main`），其他人只写自己的分支。

| 轮次  | 主干合并当值      | 规则                        |
| ----- | ----------------- | --------------------------- |
| M0–M1 | C（引擎负责人）   | 冻结契约、初始化 shared/lib |
| M2    | B（接入负责人）   | 集成对话管线与存储          |
| M3    | A（可视化负责人） | 联调精炼闭环                |
| M4    | B                 | 打包与发布收尾，之后循环    |

- 非当值人：只在 `feat/ui`、`feat/platform`、`feat/engine` 分支提交，不碰共享文件
- 当值人：负责合并、解冲突、跑通 CI，合并窗口内其他人暂停修改共享文件
- 共享文件清单：`package.json`、`package-lock.json`、`shared/types.ts`、`electron.vite.config.ts`、`tsconfig.json`、`.github/**`
- 每轮结束时交换当值人，避免单点

## 六、主要风险

| 风险                     | 对策                                         |
| ------------------------ | -------------------------------------------- |
| 接口漂移导致返工         | M0 冻结 types，加契约测试；变更需三人同意    |
| UI 等后端                | A 全程 mock 优先，接口不变即可替换           |
| 轮流写入导致分支长期分裂 | 每个里程碑必须合并一次，不跨里程碑积压       |
| 指纹/配对规则理解不一致  | 规则写进 `shared/lib` 单测，以测试为唯一解释 |
